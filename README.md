# Microsoft Sentinel UEBA Demo Kit

This kit creates bounded, synthetic Microsoft 365 activity for six to eight
lab personas so Microsoft Sentinel can build user and peer context over time.
It is intended for a dedicated demonstration tenant, not production users.

The implementation was validated with eight personas in Sales, Finance, and
Engineering. Each persona authenticates once by device code and then uses an
independent, DPAPI-encrypted MSAL token cache for silent Microsoft Graph
activity.

## What this kit includes

| File | Purpose |
|---|---|
| `DEMO-PLAN.md` | Architecture, baseline timeline, deviations, and success criteria |
| `baseline-config.sample.json` | Tenant-neutral eight-persona configuration |
| `setup-application.ps1` | Creates or reuses the public-client Entra application and writes the initial runtime configuration |
| `validate-config.ps1` | Checks placeholders, GUIDs, personas, peer groups, recipients, and scenario limits |
| `run-baseline.ps1` | Enrolls personas and generates bounded Microsoft Graph behavior |
| `install-scheduled-task.ps1` | Runs the generator hourly while the Windows user is signed in |
| `queries/validation-queries.kql` | Validates authentication, Office activity, peer mappings, and UEBA enrichment |
| `PRESENTER-CHECKLIST.md` | Readiness and live-demo checklist |

## Security model

- Use only synthetic, licensed lab identities.
- The runner never accepts or stores passwords.
- Each persona completes device-code authentication once.
- Each persona receives a separate MSAL cache.
- Token caches are encrypted with Windows DPAPI for the current Windows user.
- Caches cannot be copied to another machine or decrypted by another Windows account.
- The Entra application is a tenant-only public client.
- The application has delegated permissions only; it has no client secret,
  certificate, application permissions, or unattended identity privileges.
- The runner rejects and deletes a cache if the authenticated account does not
  match the requested persona.

## Prerequisites

### Tenant and licensing

- A disposable Microsoft Entra tenant and Azure subscription.
- Six to eight enabled, licensed synthetic users.
- Exchange Online mailboxes for mail scenarios.
- SharePoint/OneDrive provisioned for file scenarios.
- Calendars available through Exchange Online.
- Microsoft Sentinel enabled on a dedicated Log Analytics workspace.
- Licensing required for the selected Sentinel, Entra, Microsoft 365, and
  Defender features.

### Local workstation

- Windows PowerShell 5.1 or PowerShell 7.
- `Microsoft.Graph.Authentication`:

```powershell
Install-Module Microsoft.Graph.Authentication -Scope CurrentUser
```

- A Windows user profile that will own the encrypted persona caches.
- Permission to create a scheduled task if scheduling is desired.

## Step 1: Configure Sentinel and data sources

1. Enable Microsoft Sentinel on a dedicated Log Analytics workspace.
2. Enable User and Entity Behavior Analytics.
3. Select supported UEBA data sources, including Entra sign-in and audit data.
4. Configure Entra diagnostic settings or the applicable connector so these
   tables receive data:
   - `SigninLogs`
   - `AADNonInteractiveUserSignInLogs`
   - `AuditLogs`
5. Configure the Microsoft 365/Office 365 connector and verify that
   `OfficeActivity` receives Exchange, SharePoint, and OneDrive auditing.
6. Confirm these tables exist:
   - `BehaviorAnalytics`
   - `UserPeerAnalytics`
   - `OfficeActivity`
   - `SigninLogs`
   - `AADNonInteractiveUserSignInLogs`

An empty `OfficeActivity` table is a blocking gap for demonstrating enrichment
of the email, calendar, SharePoint, and OneDrive behavior generated by this
kit. Do not assume that successful Graph calls prove the Sentinel connector is
working.

## Step 2: Create the application

Sign in as an administrator who can create tenant applications:

```powershell
.\setup-application.ps1 -TenantId "<TENANT_GUID>"
```

The script:

- Authenticates with `Application.ReadWrite.All`.
- Creates or reuses `UEBA Baseline Orchestrator`.
- Enables public-client authentication.
- Adds the `http://localhost` redirect URI.
- Adds delegated Microsoft Graph permissions:
  - `User.Read`
  - `Mail.Send`
  - `Calendars.ReadWrite`
  - `Files.ReadWrite`
- Creates the service principal when necessary.
- Writes `baseline-config.json` with the tenant and client IDs.

If user consent is restricted, grant administrator consent to the delegated
permissions before enrolling personas. Do not add a client secret.

## Step 3: Insert tenant persona data

Open `baseline-config.json` and replace every `<TENANT_DOMAIN>` entry with a
real synthetic user UPN.

Recommended population:

| Peer group | Count | Intended pattern |
|---|---:|---|
| Sales | 3 | Broad workday; profile, calendar, OneDrive, frequent internal mail |
| Finance | 3 | Narrower workday; profile, calendar, OneDrive, less frequent mail |
| Engineering | 2 | Broad workday; profile, calendar, OneDrive |

Keep the `mailRecipientUpn` values inside the synthetic population. The sample
forms internal recipient rings so no external mail is sent.

Validate:

```powershell
.\validate-config.ps1
.\run-baseline.ps1 -DryRun
```

## Step 4: Enroll each persona

Enroll one persona at a time:

```powershell
.\run-baseline.ps1 -Enroll -PersonaUpn "sales.user1@contoso.onmicrosoft.com"
```

When the device-code page opens:

1. Sign out of any unintended account if necessary.
2. Authenticate as the exact persona named in the command.
3. Complete MFA and consent.
4. Wait for `ENROLLED user=<UPN>`.

Repeat for every enabled persona, then verify:

```powershell
.\run-baseline.ps1 -Status
```

Every user should report `cache=ENROLLED`.

## Step 5: Validate one live run

Run the complete population:

```powershell
.\run-baseline.ps1
```

Or one persona:

```powershell
.\run-baseline.ps1 -PersonaUpn "sales.user1@contoso.onmicrosoft.com"
```

The peer-group schedule can legitimately produce `outside-run-window`. Run the
test during the group window or temporarily adjust the sample schedule.

Review:

```powershell
Get-Content .\baseline-run.log -Tail 100
```

Expected log values include:

- `SUCCESS ... scenario=profile-read`
- `SUCCESS ... scenario=calendar-event`
- `SUCCESS ... scenario=onedrive-file`
- `SUCCESS ... scenario=sales-mail-send`
- `SUCCESS ... scenario=finance-mail-send`
- `SKIP ... reason=outside-run-window`

## Step 6: Validate Sentinel ingestion

Replace the UPNs at the top of `queries/validation-queries.kql`, then run each
query separately in the `Logs` experience for the Sentinel workspace.

Expected timing:

| Data | Table | Typical expectation |
|---|---|---|
| Device-code sign-in | `SigninLogs` | Minutes |
| Silent Graph token use | `AADNonInteractiveUserSignInLogs` | Minutes |
| Exchange/SharePoint/OneDrive audit | `OfficeActivity` | Tens of minutes; sometimes longer |
| Peer calculations | `UserPeerAnalytics` | Asynchronous |
| UEBA enrichment | `BehaviorAnalytics` | Asynchronous; requires supported source events and history |

`UserPeerAnalytics` can populate before `BehaviorAnalytics`. That means the
peer engine recognizes the users, not that every generated activity has been
enriched.

## Step 7: Automate the baseline

After all personas are enrolled and one live run succeeds:

```powershell
.\install-scheduled-task.ps1
```

The task:

- Repeats hourly.
- Runs only while the same Windows account is signed in.
- Ignores overlapping invocations.
- Stops an invocation after 15 minutes.
- Relies on the JSON schedules, probabilities, and daily caps to bound activity.

Verify installation:

```powershell
Get-ScheduledTask -TaskName "UEBA Baseline Orchestrator"
Get-ScheduledTaskInfo -TaskName "UEBA Baseline Orchestrator"
```

Run for at least 14 working days. Three to four weeks is preferred.

## Scenario behavior

| Scenario | Groups | Default probability | Daily maximum |
|---|---|---:|---:|
| Profile read | All | 100% | 2 |
| Calendar event | All | 35% | 1 |
| OneDrive file | All | 50% | 1 |
| Sales email | Sales | 50% | 1 |
| Finance email | Finance | 20% | 1 |

The selection changes between eligible invocations. Daily state prevents
unbounded duplication.

## Reauthentication

Search the log for `ReauthenticationRequired`, then re-enroll only that user:

```powershell
.\run-baseline.ps1 -Enroll -PersonaUpn "<PERSONA_UPN>"
```

## Cleanup

Remove the scheduled task:

```powershell
Unregister-ScheduledTask -TaskName "UEBA Baseline Orchestrator" -Confirm:$false
```

Delete the local state directory:

```powershell
Remove-Item -LiteralPath "$env:LOCALAPPDATA\UEBA-Baseline" -Recurse
```

Remove the Entra application and synthetic tenant resources through the
authorized tenant administrator. Do not reuse the synthetic artifacts in a
production tenant.

## Known limitations

- A single workstation produces limited IP, browser, and device diversity.
- Graph profile reads may create authentication telemetry without producing an
  `OfficeActivity` record.
- Native UEBA results are probabilistic and cannot be guaranteed on demand.
- Microsoft 365 audit ingestion must be configured separately from successful
  Graph authentication.
- The scheduled task works only under the Windows profile that owns the DPAPI
  token caches and only while that account is signed in.
- Use deterministic, entity-mapped analytics rules as a demo fallback; never
  describe those incidents as native UEBA anomalies.
